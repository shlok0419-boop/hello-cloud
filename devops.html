Unit 5

DevOps and Operations

DevOps joins development and operations so software is built, tested, and deployed in small, frequent, automated steps. This page covers the lifecycle, CI and CD, infrastructure as code, containers, monitoring, and cost control.

Lifecycle CI and CD Infrastructure as code Containers Monitoring Cost control Security habits

1. The DevOps lifecycle

DevOps is a loop, not a straight line. Each stage feeds the next, and feedback from production goes back into planning.

StageQuestion it answersTools (examples)
PlanWhat should we build next?Issues, project boards
CodeHow do we write and store it?Git, GitHub
BuildDoes it compile and package correctly?GitHub Actions, Jenkins
TestDoes it work and stay correct?Unit and integration tests
ReleaseIs this version approved?Version tags, release notes
DeployHow does it reach users?Terraform, Docker, CloudFormation
OperateHow does it run day to day?Load balancers, auto scaling
MonitorIs it healthy, and what should change?CloudWatch, Azure Monitor

The goal is a short feedback loop. A problem found in minutes by an automated test is far cheaper to fix than one found by a customer.

2. CI, continuous delivery, and continuous deployment

CI

Continuous Integration

Developers merge small changes often. Each change is built and tested automatically, so a broken change is found within minutes.

CD

Continuous Delivery and Deployment

Delivery keeps every passing change ready to release, with a manual approval step. Deployment releases every passing change to production automatically.

Commit -> Build -> Test -> Package -> Deploy to staging -> Approve -> Deploy to production
|_________ CI _________|                                    |____ CD ____|
Example

A GitHub Actions workflow file in .github/workflows/ can run on every push to main. It checks out the code, runs the tests, and reports a pass or fail on the commit.

3. Infrastructure as code (IaC)

Infrastructure as code means describing servers, networks, and storage in files. Those files can be versioned in Git, reviewed like code, and applied the same way every time.

Declarative

You describe the end state, such as "one bucket exists with this policy", and the tool works out the steps. Examples: Terraform, CloudFormation.

Imperative

You list the steps in order. Examples: a shell script, or an Ansible playbook task list.

# main.tf: a Terraform file that describes one S3 bucket
resource "aws_s3_bucket" "site" {
  bucket = "hello-cloud-shlok-2026"
}

# Commands
terraform init      # download the AWS provider
terraform plan      # show what will change, without changing anything
terraform apply     # create the resources
terraform destroy   # remove them when finished

Benefits: repeatable setups, a history of changes in Git, and easy cleanup. Cleanup matters for cost control, because you can rebuild resources when you need them.

4. Containers

A container packages an application with its libraries, but shares the host's operating system kernel. A virtual machine runs a full guest operating system on top of a hypervisor.

FeatureVirtual machineContainer
IncludesA full guest OS, the app, and its librariesThe app and its libraries, sharing the host kernel
Start timeMinutesSeconds or less
SizeGigabytesMegabytes
IsolationStrong, with a separate kernelGood, but shares the host kernel

Docker builds containers from a Dockerfile:

# Dockerfile
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html

# Commands
docker build -t hello-cloud .         # build an image from the Dockerfile
docker run -d -p 8080:80 hello-cloud  # run it, mapping host port 8080 to container port 80
docker ps                             # list running containers
docker stop CONTAINER_ID              # stop one
Lab note

Install Docker in your VM by following the official Ubuntu instructions before running these commands. Don't run containers from untrusted images.

5. Monitoring with Amazon CloudWatch

CloudWatch collects metrics (numbers over time, such as CPU use), logs (text output from services), and alarms (notifications when a metric crosses a threshold). Dashboards show several metrics together.

ConceptWhat it doesExample
MetricA measured value over timeEC2 CPUUtilization
Log groupStores log streams from a serviceWeb server access logs
AlarmTriggers when a metric breaks a thresholdEstimated charges above $5 send an email
DashboardA page of graphsCost and CPU in one view

Billing metrics appear in CloudWatch as EstimatedCharges, in the us-east-1 Region. This is where a billing alarm is created.

6. Cost control habits

  1. Set a budget and an alert first. A zero-spend or low-amount budget catches surprises early.
  2. Tag resources with a project name, so you can see which work costs money.
  3. Stop or terminate EC2 instances at the end of each session.
  4. Delete unused resources, such as old buckets, volumes, and Elastic IP addresses.
  5. Use lifecycle rules on S3 to move old files to cheaper storage classes.
  6. Right-size instances by choosing the smallest type that does the job.

7. Security habits

Least privilege

Give each user and role only the permissions it needs, such as S3 access without full admin rights.

Don't use root daily

Create an IAM user or role for everyday work, and turn on multi-factor authentication (MFA) for the root account.

Rotate and remove keys

Delete access keys you no longer use, and rotate any key that may have leaked.

Close unneeded ports

Open only the ports a service needs, and limit SSH to your own IP address where possible.
