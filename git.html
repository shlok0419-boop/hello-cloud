Unit 5

Git and GitHub

Git records the history of your files, so you can experiment and undo mistakes safely. GitHub hosts that history online and adds collaboration tools such as pull requests and GitHub Pages.

Core idea Three areas Setup Daily workflow Commit messages Branches Merge vs rebase Conflicts Undoing Remotes and GitHub .gitignore Secrets

1. The core idea

A Git repository is a folder with a hidden .git directory. That directory stores every version of every tracked file as a commit. A commit is a snapshot of the project, with an author, a time, a message, and a link to the previous commit. Each commit is identified by a long hash, and Git shows its first seven characters, such as 78562cc.

Git is distributed. Your computer holds the full history, so you can read logs and make commits without internet access. GitHub is simply another copy that you share with others.

2. The three areas of Git

Git moves changes through three areas. Most beginner confusion comes from forgetting which area a change is in.

Working directory  --git add-->  Staging area  --git commit-->  Repository  --git push-->  GitHub
  (files you edit)            (chosen changes)          (history)                    (remote copy)
AreaWhat it holdsSee it with
Working directoryThe files you are editinggit status, git diff
Staging area (index)Changes selected for the next commitgit diff --staged
Repository (.git)Every commit, branch, and taggit log --oneline
Why staging exists

Staging lets you group related changes into clean commits. You can edit three files, but commit only the one that fixes a bug, then commit the rest separately.

3. Setup and creating a repository

git --version                                    # check Git is installed
git config --global user.name "Your Name"        # author name on every commit
git config --global user.email "you@example.com" # author email
git config --global init.defaultBranch main      # new repos start on main
git config --list                                # show all settings

git init -b main                                 # start a repository in this folder
git clone https://github.com/USER/REPO.git       # copy an existing repository

4. Daily workflow

git status                        # what changed, and what is staged?
git diff                          # show the exact unstaged changes
git add index.html                # stage one file
git add .                         # stage every change in this folder
git commit -m "Add contact line"  # save a snapshot
git log --oneline                 # short history
git push                          # send commits to GitHub
Check before you commit

Run git status and read the file list. git add . stages everything, including files you did not mean to share, so check first.

5. Writing good commit messages

Write the subject in the imperative mood, as if giving an instruction ("Add", "Fix", "Update"), and keep it under about 50 characters. Add a body after a blank line when the reason is not obvious.

Good

Add networking cheat sheet

Fix contact link on about page

Weak

stuff

Updated some files and fixed things

6. Branches

A branch is a movable pointer to a commit. Create a branch to work on a feature without changing main. Prefixes such as feature/ and fix/ keep the history easy to read.

git branch                         # list local branches
git switch -c feature/about-page   # create a branch and switch to it
git switch main                    # switch back
git branch -d feature/about-page   # delete it after merging
        A---B              (main)
       /
  ----                    
       \
        C---D            (feature/about-page)

Here main and the feature branch split after commit A. Each has its own commits until one of them is merged into the other.

7. Merge vs rebase

Merge

Joins two branches. If both have new commits, Git creates a merge commit. The history shows exactly what happened. Safe for shared branches.

git switch main
git merge feature/about-page

Rebase

Replays your commits on top of another branch, giving a straight line of history. It rewrites commits, so don't rebase branches other people are using.

git switch feature/about-page
git rebase main

In this project, the About page was merged with --no-ff, which always creates a merge commit so the branch stays visible in the graph.

Golden rule

Don't rewrite history that has already been pushed and shared, unless everyone on that branch agrees.

8. Resolving a merge conflict

A conflict happens when two branches change the same lines. Git stops and marks the file like this:

<<<<<<< HEAD
<p>Contact: shlok0419@gmail.com</p>
=======
<p>Contact: hello@example.com</p>
>>>>>>> feature/contact
  1. Open the file and decide which content is correct. Delete the three marker lines.
  2. Mark it resolved with git add index.html.
  3. Finish the merge with git commit. Git fills in a default message.

Run git status at any point to see which files still have conflicts.

9. Undoing mistakes

SituationCommandEffect
Discard edits to one filegit restore fileReverts the file to the last commit. The edits are lost.
Unstage a filegit restore --staged fileKeeps the edits, removes them from staging.
Fix the last commit messagegit commit --amend -m "New message"Rewrites the last commit. Avoid it after pushing.
Undo a commit, keep changes stagedgit reset --soft HEAD~1Removes the commit, changes stay staged.
Undo a commit, keep changes unstagedgit reset --mixed HEAD~1Removes the commit, changes stay in your files.
Undo a commit and discard its changesgit reset --hard HEAD~1Destructive. The changes are gone.
Undo a pushed commit safelygit revert COMMITAdds a new commit that reverses the change. Safe for shared history.
Find a lost commitgit reflogLists recent positions of HEAD, so you can return to one.
Before any reset

Run git status and git log --oneline -3 first, and be sure you understand what will be lost.

10. Remotes and GitHub

A remote is another copy of your repository. origin is the default name for the GitHub copy.

git remote add origin https://github.com/USER/hello-cloud.git
git remote -v                    # show remote URLs
git push -u origin main          # first push, sets the upstream branch
git push                         # later pushes
git fetch origin                 # download changes without merging
git pull                         # fetch and merge the remote changes

On a team, you usually work through a pull request. You push a branch, open a pull request on GitHub, get a review, then merge. This project uses GitHub Pages, which publishes the files on main as a website.

Authentication

GitHub doesn't accept account passwords for Git. Use a Personal Access Token (Settings, Developer settings, Tokens) or an SSH key.

11. The .gitignore file

A .gitignore file lists files and folders that Git should never track, such as logs, editor files, and secrets.

# .gitignore
.DS_Store
*.log
.env
node_modules/
*.pem
*.key

A .gitignore rule only stops new files from being tracked. A file that was already committed stays in history until you remove it.

12. Never commit secrets

Deleting a file in a later commit doesn't remove it from history. Anyone who can clone the repository can still read the old version.

If a secret is pushed

Revoke or rotate the key or password first. The leaked value is already compromised, so cleaning the history alone is not enough.

Keep ~/.ssh and ~/.aws outside any repository, and never paste keys or passwords into chats or commit messages.

Practice

  1. Create a branch feature/practice, add a file, commit it, switch back to main, and merge it. Then run git log --oneline --graph --all.
  2. Create a deliberate conflict by editing the same line on two branches. Merge, resolve the conflict, and commit.
  3. Make a commit, then undo it with git revert. Compare the history before and after.
  4. Use git reflog to find a commit you reset away, then recover it.
